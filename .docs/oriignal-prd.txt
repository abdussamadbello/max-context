1. Overview
This document specifies the Go implementation of the Maximum Context MCP server — the core runtime binary that provides call-graph intelligence and full-text code search to Claude Code via the Model Context Protocol. The server is compiled to a single static binary per platform and distributed inside an npm wrapper package that handles Claude Code plugin integration (hooks, skills, manifest).
The Go binary owns all computationally intensive work: Tree-sitter AST parsing, SQLite database management, FTS5 full-text search, file system watching, artifact generation, and MCP JSON-RPC communication over stdio. Shell hook scripts and markdown skill files remain outside the binary in the npm package.
1.1 Why Go
Concern	Node.js (original)	Go
Distribution	npm install with native modules (better-sqlite3, tree-sitter)	Single static binary, zero runtime deps
Install failure rate	~5–10% on exotic platforms due to native compilation	~0% — precompiled for every OS/arch
Startup time	~300–500ms (Node.js boot + module load)	~10–20ms (compiled binary)
Memory at idle	~50–80MB (V8 heap)	~5–10MB
Concurrency model	Single-threaded event loop + worker threads	Goroutines + channels (native parallelism)
Cross-compilation	Requires per-platform native builds	GOOS/GOARCH from single machine
SQLite	better-sqlite3 (native addon)	modernc.org/sqlite (pure Go, zero CGO)
Tree-sitter	Native addon per grammar	CGO bindings compiled into binary

1.2 Scope
This PRD covers only the Go binary (max-context). It does not cover the npm wrapper package, hook scripts, skill markdown files, or the plugin manifest, which are specified in the main Maximum Context PRD. The Go binary is consumed by the npm package as a platform-specific dependency downloaded at install time.

2.2 Runtime Architecture
The binary runs as a long-lived stdio process spawned by Claude Code. It manages three concurrent subsystems connected via Go channels:

Subsystem	Goroutine(s)	Responsibilities
MCP Server	1 (main)	Read JSON-RPC from stdin, dispatch to tool handlers, write responses to stdout
File Watcher	1	fsnotify events → debounce → send file paths to reindex channel
Reindex Worker	1	Consume from reindex channel → Tree-sitter parse → SQLite update → FTS rebuild

All three subsystems share the SQLite database connection via WAL mode, which allows concurrent readers with a single writer. The reindex worker is the only writer; MCP tool handlers are read-only during query execution.
2.3 Concurrency Model
func main() {
    db := db.Open(".context/index.db")
    reindexCh := make(chan string, 100)  // buffered: file paths to reindex

    // Start file watcher
    go watcher.Run(reindexCh)

    // Start reindex worker
    go indexer.RunWorker(db, reindexCh)

    // Run MCP server on main goroutine (blocks on stdin)
    mcp.Serve(db, os.Stdin, os.Stdout)
}

The reindex channel is buffered at 100 entries. If the developer saves 50 files at once (e.g. git checkout), all paths are queued and processed sequentially by the single worker. This prevents concurrent writes to SQLite and keeps the database consistent without explicit locking.

3. MCP Protocol Implementation
3.1 Transport: stdio
The MCP server communicates via stdin/stdout using newline-delimited JSON-RPC 2.0 messages. Each message is a single JSON object followed by a newline character. The server reads from os.Stdin using a bufio.Scanner and writes responses to os.Stdout using json.Encoder.

Critical: The binary must never write anything to stdout that is not a valid JSON-RPC message. All diagnostic output, logs, and errors go to stderr. Any stray stdout output will corrupt the MCP protocol stream and crash the Claude Code session.
3.2 Required Methods
Method	Direction	Purpose
initialize	Client → Server	Handshake: exchange capabilities and protocol version
initialized	Client → Server	Notification confirming init complete
tools/list	Client → Server	Return tool schemas (query_codebase, get_call_chain)
tools/call	Client → Server	Execute a tool and return results
notifications/cancelled	Client → Server	Cancel in-progress tool call
ping	Client → Server	Health check; respond with empty result

3.3 Initialize Response
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2024-11-05",
    "capabilities": {
      "tools": { "listChanged": false }
    },
    "serverInfo": {
      "name": "max-context",
      "version": "0.1.0"
    }
  }
}

The server advertises only the tools capability. It does not implement resources, prompts, or sampling. listChanged is false because the tool set is static at compile time.
3.4 Tool Schemas
The tools/list response must include JSON Schema for each tool’s input parameters. These schemas are embedded in the binary as Go struct literals. Total schema size budget: under 1,000 tokens combined, because every tool schema is injected into Claude’s system prompt and competes for context window space.

Tool	Estimated Schema Size	Parameters
query_codebase	~400 tokens	query (string, required), max_results (int, 5), scope (string, all), file_filter (string, null)
get_call_chain	~350 tokens	function_name (string, required), direction (string, both), depth (int, 2)

3.5 Error Handling
All errors returned via JSON-RPC error objects with standard codes:
Code	Meaning	When
-32700	Parse error	Malformed JSON on stdin
-32601	Method not found	Unknown method name
-32602	Invalid params	Missing required param or bad type
-32603	Internal error	SQLite error, Tree-sitter crash, panic recovery
-32001	Index not ready	No index.db exists; run /index-codebase first

The server must never crash. All panics are recovered at the tool handler boundary and returned as internal errors. The MCP connection must survive individual tool failures.


4. Tool Implementations
4.1 query_codebase
SQL Query
SELECT f.id, f.name, f.file_path, f.start_line, f.end_line,
       f.exported, f.language,
       snippet(functions_fts, 2, '»', '«', '...', 30) AS context,
       bm25(functions_fts, 10.0, 5.0, 1.0, 2.0) AS rank
FROM functions_fts
JOIN functions f ON f.id = functions_fts.rowid
WHERE functions_fts MATCH ?
ORDER BY rank
LIMIT ?

BM25 column weights: name (10.0) > file_path (5.0) > code (1.0) > docstring (2.0). The snippet function extracts 30 tokens of context around the match, using » and « as highlight markers.
Response Enrichment
After the FTS query returns matching functions, the tool performs a single additional query to attach 1-hop caller and callee names from the calls table. This is a batched query using WHERE caller_id IN (?) for callees and WHERE callee_id IN (?) for callers. The enrichment adds ~50–100 tokens per result but saves Claude a separate get_call_chain call in most cases.
Scope Filtering
Scope Value	Behavior
all (default)	Search functions_fts and types_fts, merge results by rank
functions	Search functions_fts only
types	Search types_fts only
files	Search file_summaries by file_path and top_functions columns

Response Budget
Target: under 2,500 tokens for 5 results. Each result includes: name, file_path, start_line, kind, exported, snippet (30 tokens), callers array (names only), callees array (names only). The raw function code is never included in search results — Claude can read the file if it needs the full implementation.
4.2 get_call_chain
SQL Query (Recursive CTE)
-- Callers (upstream): who calls this function?
WITH RECURSIVE callers(id, name, file_path, line, depth) AS (
  SELECT f.id, f.name, f.file_path, f.start_line, 0
  FROM functions f WHERE f.name = ?
  UNION ALL
  SELECT f.id, f.name, f.file_path, f.start_line, c.depth + 1
  FROM callers c
  JOIN calls e ON e.callee_id = c.id
  JOIN functions f ON f.id = e.caller_id
  WHERE c.depth < ?
)
SELECT DISTINCT id, name, file_path, line, depth FROM callers
ORDER BY depth, name;

-- Callees (downstream): what does this function call?
WITH RECURSIVE callees(id, name, file_path, line, depth) AS (
  SELECT f.id, f.name, f.file_path, f.start_line, 0
  FROM functions f WHERE f.name = ?
  UNION ALL
  SELECT f.id, f.name, f.file_path, f.start_line, c.depth + 1
  FROM callees c
  JOIN calls e ON e.caller_id = c.id
  JOIN functions f ON f.id = e.callee_id
  WHERE c.depth < ?
)
SELECT DISTINCT id, name, file_path, line, depth FROM callees
ORDER BY depth, name;

Unresolved Callees
When callee_id is NULL (external library call, dynamic dispatch), the callee appears in results with file_path set to "(external)" and line set to null. This preserves visibility into the function’s dependencies without requiring the external library to be indexed.
Response Budget
Target: under 500 tokens for depth 2. Results are grouped by depth level. Each node is: name, file_path, line. No code snippets — just the map. Claude knows exactly which files to open if it needs more detail.
4.3 Internal Tool: reindex
Not exposed via MCP (not in tools/list). Called internally by the reindex worker goroutine when files change. Accepts a file path, re-parses with Tree-sitter, and performs a transactional update of all affected rows in functions, calls, types, imports, and file_summaries tables. Rebuilds FTS for affected rowids.


5. Indexer
5.1 Full Index Pipeline
Triggered by the /index-codebase skill, which invokes the binary with a --index flag. The pipeline runs sequentially:

1.Scan: Walk project directory, filter by language extension, respect .gitignore and .contextignore
2.Parse: For each file, run Tree-sitter parser with language-specific grammar. Extract functions, types, imports, and call edges.
3.Store: Insert extracted data into SQLite tables within a single transaction. 1,000 files × 4 tables = 4,000+ INSERTs, all committed atomically.
4.Resolve: Match callee_name strings against known function names to populate callee_id foreign keys. Uses a hash map of name → []function_id for O(1) lookup.
5.FTS Rebuild: INSERT INTO functions_fts(functions_fts) VALUES('rebuild') to repopulate the full-text index.
6.Artifacts: Generate architecture.md, summary.md, and status.json from aggregated index data.
7.Report: Write indexing summary to stdout (function count, file count, duration). Claude sees this as the skill output.
5.2 Incremental Index
Triggered by file watcher or PostToolUse hook (which sends a file path to the binary via a lightweight mechanism — see Section 8). The incremental pipeline:

8.Delete all rows in functions, calls, types, imports where file_path = changed file
9.Re-parse the single file with Tree-sitter
10.Insert new rows
11.Re-resolve callee_id for edges involving this file (both as caller and as callee)
12.Rebuild FTS (full rebuild is <1s for the entire index; incremental FTS is not supported by SQLite FTS5 content-sync tables)
13.Update file_summaries for the changed file
14.Append to changes table
15.Regenerate summary.md (reads from DB, writes file)
16.Update status.json (clear this file from dirtyFiles, update timestamp)

Performance target: Full incremental reindex of a single file completes in under 100ms. This includes Tree-sitter parse (~5–50ms), SQLite transaction (~1–5ms), FTS rebuild (~10–50ms depending on total index size), and artifact regeneration (~1–5ms).
5.3 Tree-sitter Query Patterns
Each language defines extraction patterns using Tree-sitter’s S-expression query syntax. Patterns are embedded as .scm files in the binary via Go’s embed directive. The patterns extract four categories of nodes:

Category	TypeScript Example Patterns	Extracted Fields
Functions	(function_declaration name: (identifier) @name) (arrow_function) (method_definition name: (property_identifier) @name)	name, start_line, end_line, code, exported
Calls	(call_expression function: (identifier) @callee) (call_expression function: (member_expression property: (property_identifier) @callee))	callee_name, caller context
Types	(interface_declaration name: (type_identifier) @name) (type_alias_declaration name: (type_identifier) @name)	name, kind, definition, exported
Imports	(import_statement source: (string) @path) (import_clause (named_imports (import_specifier name: (identifier) @symbol)))	imported_path, imported_symbols

5.4 Language Support Matrix
Language	Go Grammar Package	Priority	CGO Required
TypeScript / TSX	github.com/smacker/go-tree-sitter/typescript	P0	Yes (compiled in)
JavaScript / JSX	github.com/smacker/go-tree-sitter/javascript	P0	Yes (compiled in)
Python	github.com/smacker/go-tree-sitter/python	P0	Yes (compiled in)
Go	github.com/smacker/go-tree-sitter/golang	P1	Yes (compiled in)
Rust	github.com/smacker/go-tree-sitter/rust	P1	Yes (compiled in)
Java	github.com/smacker/go-tree-sitter/java	P2	Yes (compiled in)

All Tree-sitter grammars are compiled into the binary at build time via CGO. The final binary includes all P0 and P1 grammars. Users do not install grammars separately. The binary auto-detects file language from extension and selects the appropriate grammar.


6. SQLite Database
6.1 Connection Configuration
PRAGMA journal_mode = WAL;           -- concurrent reads during writes
PRAGMA synchronous = NORMAL;         -- safe with WAL, faster than FULL
PRAGMA cache_size = -8000;           -- 8MB page cache
PRAGMA mmap_size = 268435456;        -- 256MB memory-mapped I/O
PRAGMA busy_timeout = 5000;          -- 5s retry on lock contention
PRAGMA foreign_keys = ON;
PRAGMA temp_store = MEMORY;

WAL mode is essential: it allows the MCP server goroutine to execute read queries (tool calls) while the reindex worker goroutine writes updates. Without WAL, read queries would block during writes, causing tool call latency spikes.
6.2 Schema (Identical to Main PRD)
The Go binary creates and migrates the schema on startup. Schema version is tracked in a meta table:
CREATE TABLE IF NOT EXISTS _meta (
  key TEXT PRIMARY KEY,
  value TEXT
);
-- On startup:
-- SELECT value FROM _meta WHERE key = 'schema_version';
-- If NULL or < current: run migrations
-- INSERT OR REPLACE INTO _meta VALUES ('schema_version', '3');

Migration functions are Go functions keyed by version number. Each migration runs in a transaction. If a migration fails, the transaction rolls back and the server exits with an error on stderr. The user re-runs /index-codebase to rebuild.
6.3 Prepared Statements
All SQL queries are prepared once at startup and cached for the lifetime of the process. The queries.go file exports a Queries struct:
type Queries struct {
    SearchFunctions    *sql.Stmt  // FTS5 MATCH + BM25
    SearchTypes        *sql.Stmt  // types_fts MATCH
    GetCallers         *sql.Stmt  // recursive CTE, callers
    GetCallees         *sql.Stmt  // recursive CTE, callees
    GetCallersOf       *sql.Stmt  // 1-hop callers for enrichment
    GetCalleesOf       *sql.Stmt  // 1-hop callees for enrichment
    InsertFunction     *sql.Stmt
    InsertCall         *sql.Stmt
    InsertType         *sql.Stmt
    InsertImport       *sql.Stmt
    InsertFileSummary  *sql.Stmt
    InsertChange       *sql.Stmt
    DeleteByFile       *sql.Stmt  // DELETE FROM functions WHERE file_path = ?
    GetDirtyFiles      *sql.Stmt  // files with mtime > last_indexed_at
    GetStats           *sql.Stmt  // COUNT(*) from functions, files, etc.
}

6.4 Pure Go SQLite: modernc.org/sqlite
The binary uses the pure-Go SQLite implementation from modernc.org/sqlite. This eliminates the CGO dependency for SQLite (CGO is still required for Tree-sitter but not for database access). Key properties:
•Zero CGO for SQLite operations — compiles to any GOOS/GOARCH without a C compiler for the database layer
•FTS5 is included and enabled by default
•Performance is within 10-20% of the C SQLite via mattn/go-sqlite3 for typical query workloads
•WAL mode works correctly
•The database/sql standard library interface is used, making it trivial to swap implementations if needed


7. File Watcher
7.1 Core Implementation
The watcher goroutine uses fsnotify to monitor the project’s source directories. On startup, it recursively adds all directories matching the configured language extensions.

Property	Value
Library	github.com/fsnotify/fsnotify
Events watched	Create, Write, Remove, Rename
Debounce window	500ms (per file path)
Ignored paths	node_modules, .git (contents), .context, dist, build, vendor, __pycache__
Watched extensions	Configured per project; defaults: .ts, .tsx, .js, .jsx, .py, .go, .rs, .java

7.2 Debounce Strategy
File saves often trigger multiple fsnotify events (write, chmod, rename-swap). The watcher maintains a map[string]time.Timer keyed by file path. When an event arrives:

17.If no timer exists for this path, create one with a 500ms delay.
18.If a timer already exists, reset it to 500ms.
19.When the timer fires, send the file path to reindexCh.

This ensures a file saved rapidly (e.g., auto-save every 100ms) triggers only one reindex, 500ms after the last write settles.
7.3 Git-Aware Bulk Invalidation
In addition to source files, the watcher monitors .git/HEAD (branch switches) and .git/index (staging changes from pull/merge/rebase). When these files change:

20.Run git diff --name-only HEAD@{1} HEAD to identify changed files.
21.If fewer than 50 changed files: send each to reindexCh for sequential processing.
22.If 50 or more: set status.json to reindexInProgress: true, send all paths to a separate bulk reindex function that runs in a single transaction, then reset status.

During bulk reindex, status.json reports unhealthy and the Grep interceptor hook allows all grep calls through.
7.4 New Directory Detection
When a Create event fires for a directory (detected via os.Stat), the watcher recursively adds the new directory and all its subdirectories to fsnotify. This handles the case where a developer creates a new src/feature/ directory — files created inside it are immediately watched.


8. Hook Communication
The Go binary is invoked by Claude Code as the MCP server process. Hook scripts (.sh files in the npm package) need to communicate with the running binary for certain operations. Two integration patterns are used:
8.1 PostToolUse Hook → Binary
When Claude edits a file, the PostToolUse hook needs to notify the running MCP server to reindex that file. Rather than implementing a secondary IPC channel, the hook writes the changed file path to a well-known trigger file:
#!/bin/bash
# post-write-reindex.sh
FILE_PATH=$(echo "$TOOL_INPUT" | jq -r '.file_path // .path // empty')
if [ -n "$FILE_PATH" ]; then
  echo "$FILE_PATH" >> .context/.reindex-queue
fi

The file watcher in the Go binary monitors .context/.reindex-queue via fsnotify. When it changes, the watcher reads all lines, sends each path to reindexCh, and truncates the file. This avoids the need for Unix sockets, HTTP servers, or named pipes while remaining cross-platform.
8.2 Grep Interceptor Hook
The grep-interceptor.sh script reads .context/status.json directly from disk. It does not communicate with the running binary — the binary keeps status.json current, and the hook reads the file. This is a pure data-sharing pattern with no IPC.
8.3 SessionStart Hook
The session-start.sh script reads .context/summary.md and outputs it to stdout. If the index is stale (detected by comparing file mtimes against a timestamp in status.json), it writes stale file paths to .context/.reindex-queue, which the running binary’s watcher picks up.
8.4 Binary CLI Flags
The binary supports multiple invocation modes via flags:
Flag	Mode	Used By
(no flags)	MCP stdio server (long-running)	.mcp.json command entry
--index	Full index pipeline (batch, exits on completion)	/index-codebase skill
--reindex <path>	Single-file reindex (batch, exits)	PostToolUse hook (alternative to queue file)
--status	Print status.json to stdout (exits)	Hook scripts for health check
--version	Print version and exit	Diagnostics



9. Artifact Generation
9.1 architecture.md
Generated by internal/artifacts/architecture.go. Queries the database and produces a markdown file. Data sources:

Section	SQL Source	Logic

9.2 summary.md
Generated by internal/artifacts/summary.go. Template-based. Kept under 50 lines. Regenerated after every incremental reindex. Uses Go’s text/template with data from:
•_meta table: project name, last full index time
•functions table: COUNT(*)
•file_summaries table: COUNT(*)
•calls table: top 5 by in-degree
•changes table: last 5 entries filtered by current session_id
•test_coverage (if populated): untested function names
9.3 status.json
Written atomically (write to temp file, rename) to prevent partial reads by hook scripts. Updated after every reindex operation and file watcher event. The Go binary holds the canonical state in memory and flushes to disk on mutation.

10.4 Postinstall Binary Download
The install.js script detects os.platform() and os.arch(), constructs the download URL from a GitHub Releases pattern, downloads the binary, verifies a SHA256 checksum, and places it in ./bin/. The .mcp.json command entry points to ./bin/max-context.

// install.js (simplified)
const platform = process.platform;   // darwin, linux, win32
const arch = process.arch;           // arm64, x64
const version = require('./package.json').version;
const url = `https://github.com/maxcontext/max-context/releases/download/
  v${version}/max-context-${platform}-${arch}${ext}`;
// Download, verify SHA256, chmod +x, write to ./bin/

This is the same pattern used by esbuild, Turbo, SWC, and Prisma for distributing platform-specific binaries via npm.

12. Testing Strategy
12.1 Unit Tests
Package	Key Test Cases
internal/indexer	Parse TypeScript file → correct function/call extraction; parse Python → class methods detected; parse Go → methods on structs detected; empty file → no crash; binary file → skipped
internal/db	Schema creation on empty DB; migration from v1 to v2; FTS5 search returns BM25-ranked results; recursive CTE traverses 3 levels; concurrent read during write (WAL test)
internal/tools	query_codebase returns top-5 by relevance; get_call_chain returns correct callers at depth 2; unresolved callee shows as external; empty index returns helpful error, not crash
internal/mcp	JSON-RPC parse/serialize roundtrip; unknown method returns -32601; malformed JSON returns -32700; tools/list returns both tool schemas; tools/call dispatches correctly
internal/watcher	File change triggers reindex after debounce; rapid saves trigger single reindex; .git/HEAD change triggers bulk invalidation; ignored paths do not trigger
internal/artifacts	architecture.md contains top functions; summary.md is under 50 lines; status.json is valid JSON; atomic write does not leave partial files

•Spawn the binary as a subprocess, send MCP messages via stdin, assert responses on stdout
•Full index pipeline on a fixture TypeScript project (50 files, ~5K LOC), then run tool queries and validate results against hand-verified expected outputs
•Modify a fixture file while the binary is running, wait 1 second, query for the change, assert the index reflects it
•Simulate branch switch by modifying .git/HEAD fixture, assert bulk reindex triggers

14. Release Process
23.Tag the Go repository: git tag v0.1.0
24.GoReleaser builds binaries for all 6 platform targets and uploads to GitHub Releases with SHA256 checksums
25.Update the npm package’s package.json version to match
26.npm publish — users run npm install or claude plugin install, postinstall downloads the matching binary
27.CI verifies: binary downloads succeed for all platforms, MCP handshake completes, full index + query roundtrip passes

Version numbers are kept in sync between the Go binary (--version) and the npm package (package.json). The postinstall script uses the npm package version to construct the GitHub Releases download URL.
